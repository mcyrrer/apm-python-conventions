# Database conventions

When working with a database, or with SQLAlchemy, Alembic, or PostgreSQL config
(compose files, Dockerfiles, CI) in this project, follow these rules. Full setup
recipes and the ready-to-copy CI workflow live in the `database-migrations`
skill — load it when adding a data layer or migrations.

- **ORM: SQLAlchemy** is the default database toolkit. Use typed 2.0-style models
  (`Mapped[...]` + `mapped_column`) and a single `sessionmaker`; hand sessions to
  callers via a dependency, not module-level globals.
- **Migrations: Alembic** for every schema change. Never hand-edit a live schema
  and never rely on `Base.metadata.create_all` in production. Review each
  autogenerated migration before committing — confirm it captures the intended
  change and nothing spurious.
- **Migration integrity is CI-enforced.** Whenever you add Alembic to a repo, you
  must also add the **migration-tests GitHub Actions workflow** (from the
  `database-migrations` skill / its `assets/migration-tests.yml`). It runs
  `alembic upgrade head` on a fresh database, `alembic check` to catch model
  drift not captured in a migration, and a downgrade→upgrade roundtrip. Alembic
  setup is not "done" until this workflow is in place.
- **PostgreSQL defaults to version 17.** Pin `postgres:17` in docker-compose, CI
  service containers, and images unless the project already standardizes on
  another version.
