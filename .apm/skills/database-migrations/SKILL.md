# Database & migrations

Set up the data layer the way this project standardizes it. The always-on rules
are in `database.instructions.md`; this skill is the deeper "how", with snippets
in `references/` and a ready-to-copy CI workflow in `assets/`.

## Defaults at a glance

- **ORM:** SQLAlchemy, typed 2.0 models (`Mapped[...]` / `mapped_column`), one
  `sessionmaker`, sessions handed out via a dependency.
- **Migrations:** Alembic for every schema change; review autogenerated
  migrations before committing.
- **Database:** PostgreSQL **17** (`postgres:17`) in compose, CI, and images.
- **Non-negotiable:** adding Alembic means also adding the **migration-tests
  workflow**. Setup isn't done without it.

## Setting up the data layer

1. **Models & session.** Define typed models on a shared `Base` and create the
   engine + `sessionmaker`; expose a session dependency. See
   `references/sqlalchemy.md`.
2. **Initialize Alembic.** `alembic init`, point `env.py` at your models'
   `metadata` and the runtime `DATABASE_URL`, then autogenerate the first
   migration. See `references/alembic.md`.
3. **Local Postgres 17.** Run `postgres:17` (compose or a container) for
   development and for generating/verifying migrations.
4. **Install the migration-tests workflow — always.** Copy
   `assets/migration-tests.yml` into the consumer repo's
   `.github/workflows/migration-tests.yml` and adjust the install step /
   package name. What it checks and why is in `references/migration-tests-ci.md`.
5. **Verify locally** before pushing: `alembic upgrade head`, then
   `alembic check` (must report no new operations), and a
   downgrade→upgrade roundtrip on the latest revision.
